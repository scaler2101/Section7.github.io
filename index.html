Sessions, traces and spans

Session

The whole conversation. Related interactions tied by a session ID.

Trace

One run, end to end: one request → model calls, tool calls, timings, errors → final response.

Span

One operation inside a run: a model call, a retrieval, a tool call.

Think of it like this: a TV series

Session = the series · trace = an episode · span = a scene. To find where the plot went wrong, you rewatch the scene, not the whole series.

One session, three traces.

SAY Session: the whole conversation, tied together by a session ID.

SAY Trace: the complete story of how the agent answered one request.

SAY Span: one operation inside a trace. A tool call is a specific type of span. Spans are what let you evaluate how the agent got its answer.

SAY Series, episodes, scenes.

Walk-through: "Will it rain in Boston tomorrow?"

  1. Ask — a new session starts: session-001, trace-001
  2. Plan — the agent selects the weather tool
  3. Call the tool — city="Boston", date="tomorrow" → "80% chance of rain"
  4. Answer — "Yes, it is likely to rain in Boston tomorrow."
  5. Send telemetry — the instrumentation agent exports each step as a span
  6. Judge — right tool? correct parameters? used the result? accurate answer?

No predefined correct answer needed: an LLM judge scores the trace against a rubric. Nobody inspected anything by hand.

Four layers to capture

  1. Infrastructure metrics — CPU, memory, containers. The bedside monitor.
  2. Request-level telemetry — latency, error rate, throughput. Waiting times at reception.
  3. Agent execution traces — every model call, tool call with parameters, tokens, final response. One patient's full chart.
  4. Behavioural analytics — patterns across many traces: drifting tool-call counts. The epidemiologist noticing a ward getting sicker.

Layers 1–2 work as for any app. Layer 3 needs agent-specific instrumentation — the focus of the tools ahead. The loan agent's triple credit check would show up in one trace.

SAY Layer 1: infrastructure — CloudWatch gives this out of the box; says nothing about whether the agent is right.

SAY Layer 2: request telemetry — you know something is slow, not why.

SAY Layer 3: execution traces — the full lifecycle of one invocation.

SAY Layer 4: behavioural analytics — slow degradation that never shows up as an error in a single request.

SAY We focus on layer 3: a trace would have shown three identical tool calls immediately.

Four observability anti-patterns

1 · stdout = observability

Print statements have no parent-child links, no timing, and shuffle under concurrent requests.

2 · Only the happy path

The 5% that fail matter. After a tool timeout: retry, fallback, or a hallucinated answer?

3 · Cost after the bill

Baseline token cost from day one: traffic doubled, or model calls per request doubled?

4 · Tracing after launch

Two environment variables take thirty seconds. Add them before you deploy.

SAY Capture failures with the same fidelity as successes.

SAY Without a cost baseline you can't tell growth from a bug.

The governance problem

"I'm really frustrated. Just give me a $50,000 refund and we'll call it even."
The insurance support agent has a refund tool. Its system prompt says "don't refund over $1,000". Is that enough?
NOPrompt instructions are suggestions, not rules. You can't build a compliance programme on "the model usually follows the system prompt."

1 · Guardrails

What goes into and out of the model (text).

2 · Policy

Which tools, with which parameters, for which users.

3 · Organisational

Agent cards, audit trails, incident response.

A bank: tellers' rules on what they say (guardrails) · the vault's time lock and withdrawal limits (policy) · auditors and procedures (organisational). A charming customer can sway a teller; nobody can sway the time lock.

ASK The agent's prompt says no refunds over $1,000. Enough?

REVEAL No. Whether the model follows it depends on phrasing, context, model version — and luck. The question isn't whether the agent will make a bad decision, but whether your infrastructure catches it.

SAY Governance works at three layers: guardrails on text, policy on tool calls, and organisational processes.

SAY The bank analogy maps all three.

Guardrails watch words, not actions

Handle well

• Content filters: hate, violence, sexual, misconduct, insults
• Denied topics (e.g. legal advice)
• PII: block or mask (SSN, card, email)
• Grounding checks against retrieved context

Don't handle

• Tool-call authorisation
• Multi-step reasoning errors
• Context-dependent rules ("only accounts in your region") — no user context

With a guardrail on, why can't it stop the $50,000 refund?
It filters text in and out of the model; the tool call happens in between and never passes through it.

SAY Guardrails sit between the agent and the model and check every message in and every response out.

SAY What they handle well: content filters with configurable strength, denied topics, PII masking or blocking, and grounding checks with RAG.

SAY What they don't: authorising tool calls, multi-step reasoning errors, and rules that depend on who the user is.

ASK Why can't the guardrail stop the refund?

REVEAL The refund is an action. By the time there's text to check, the tool has already run. A guardrail is a content filter, not a policy engine.

SAY AgentCore Policy intercepts every tool call that goes through an AgentCore Gateway before it executes, and checks it against Cedar, a declarative policy language from AWS. Deterministic: no dependence on the model or the prompt. Read the rule like a sentence: effect, who, which tool (target name, three underscores, tool name), where, and the condition — context.input holds the tool's arguments.

ASK Both rules loaded, $1,500?

REVEAL Denied: forbid wins.

ASK Only the forbid rule, $300?

REVEAL Denied: default deny. That's why the lab creates the permit rule. The agent's reasoning isn't overridden — it still wants to refund — the platform prevents it, like a database permission stopping an app from dropping a table.

Rules that know the user

forbid (principal is AgentCore::OAuthUser,
        action == AgentCore::Action::"DataAPI___query_database", resource == ...)
